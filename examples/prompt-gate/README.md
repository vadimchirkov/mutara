# Fixed prompt candidates → Mutara gate → final audit

Mutara acts as a durable judge/promotion layer. This example classifies customer
messages as `cancel` or `other`; it never cancels anything. An external proposer
supplies a fixed JSON list. The adapter measures predictions, applies the host's
quality rule, accounts for cost, and journals decisions. It uses only public
`teob-mutara` imports and adds no dependency or core API.

## Run the offline protocol check

```sh
pnpm run build
node examples/prompt-gate/run.mjs ./prompt-gate-v1.db prompt-gate-v1
# Identical command resumes/reads both stages without calling the executor again.
```

The two prompts in `proposals.json` are hand-authored. Responses in `fixtures/`
are explicitly scripted, not captured from an LLM or generated by GEPA. Each row
is `[id, text, expectedLabel, [initialOutput, candidate1Output, candidate2Output]]`.
There are 8 training, 8 validation and 8 final-test cases. These tiny illustrative
sets test wiring and failure modes; they are not a benchmark.

Expected scripted outcome:

| Prompt | Training accuracy | Validation accuracy | Decision |
|---|---:|---:|---|
| Initial | 50% | 50% | Baseline |
| Candidate 1 | 100% | 25% | Reject |
| Candidate 2 | 87.5% | 87.5% | Accept |

The final audit reports 50% for the initial prompt, 25% for the training-only
winner, and 87.5% for the promoted prompt. **Those are fixture expectations,
not measured gains or a comparison against GEPA.** The two selection rules share
the same candidate pool and saved selection outputs. The final test compares
their selected prompts on the same cases; it does not choose another winner.

## Protocol

1. Freeze the candidate list and its provenance before selection. `propose` only
   reads this list; it never makes an unjournaled model call.
2. Run baseline and candidate on paired training and validation cases. Require
   strictly better accuracy on both and no increase in false cancellations on
   either. This is an explicit heuristic rule, not a significance guarantee.
3. Finish selection, then load the final-test file. Its inputs and labels are
   absent from the selection plan and artifact. Build a separate experiment
   under `<id>/final-test`; every decision there is report-only (`accepted: false`).
4. Apply `selected.champion.config.prompt` in the host only after reviewing the
   audit. Mutara's experiment champion does not change the running application.

Validation participates in promotion, so it is not a final holdout. Reusing this
small validation set can overfit. Once a final-test result informs another prompt
revision, that set is no longer an untouched test for the revision. Exact duplicate
IDs and normalized texts are rejected across splits. This does not detect semantic
duplicates, related customers, temporal overlap or other domain-specific leakage.

The executor receives only `{ prompt, text }` and `{ id, costLimit }`. Labels stay
in the evaluator. The fixture executor's recorded implementation includes scripted
predictions for its own stage; it is a test double, not an independent learner.

## Connect a real executor and proposer

Replace `proposals.json` with fixed prompt strings from your proposer and record
its version, settings and generation artifact under `provenance`. Ax does have
a [GEPA implementation](https://github.com/ax-llm/ax); this example does not run it
or implement export of arbitrary Ax programs. Export the complete instructions
your runner will execute. Generation costs belong to the upstream run and must
be included separately in any end-to-end cost comparison.

Replace the illustrative case files with your labeled task. The fixture-output
columns are ignored when using a real executor. Supply an ESM module exporting:

```js
import { classify, implementation } from "./your-existing-runner.mjs";

export const executor = {
  implementation, // Pin runner source/dependencies, model ID and generation settings.
  recovery: "manual", // Paid calls without genuine provider idempotency.
  costLimit: 0.01,     // Example budget units; enforce the cap inside classify.
  budget: 2,         // CLI total for selection + final audit, in the same units.
  async execute({ prompt, text }, { id, costLimit }) {
    const { label, cost } = await classify({ prompt, text, id, costLimit });
    return { output: label, cost }; // label must be exactly "cancel" or "other".
  },
};
```

`classify` is the host integration point, not a function supplied by this example.
Read credentials from the host environment; never put them in `implementation`.

```sh
node examples/prompt-gate/run.mjs ./real-prompts-v1.db real-prompts-v1 ./executor.mjs
```

Selection uses `2 × candidates × (training cases + validation cases)` logical
calls. Final audit uses `2 × distinct selected prompts × final-test cases` calls.
The fixture makes 64 + 32 = 96 calls. The CLI gives the final audit the remaining
budget after selection; each stage reserves a full paired trial before starting.
Direct factory users set their own per-experiment budgets. Reported `spent` is
cumulative across resumes, not the amount spent by the latest invocation.

Keep the same experiment ID, source, model settings and data to resume. Changed
behavior requires a new ID; retain old journals and runnable artifacts. If a paid
call has an unknown outcome, manual recovery blocks. Reconcile its actual receipt
with the harness using the original adapter; see
[operations](../../skills/mutara/references/operations.md). The example cannot undo
provider charges. A separate journal makes the final audit resumable too.

## Why no `optimize({ holdout: ... })` yet

The shipped classifier template already supports independent validation through
`Adapter.jobs` and `assess`. Its strengthened demo now rejects a training winner
that regresses on validation. This prompt example adds a different rule (false
cancellations), fixed external proposals, and a final report that never promotes.
Existing contracts cover both without changing `src/`.

A boolean `holdout` would conflate promotion validation with final reporting and
would not encode either domain's quality constraints. No new public abstraction
is justified by these examples. Consider one only when real integrations repeat
the same data allocation, budget and reporting contract. A real, budget-matched
GEPA comparison remains a separate experiment; GEPA already performs selection,
so “GEPA accepts every candidate” is not a valid baseline description.
