The problem

Optimizers find changes. Nothing decides if they're safe to ship.

Teams that run self-improvement loops on agents hit the same failures. These come from published runs, not hypotheticals.

The prompt memorizes the training set

On Terminal-Bench 2.0 a GEPA-optimized system prompt grew from 5 to 195 lines, with task IDs, file paths and exact error strings written in.

arXiv 2607.14004

The score rises, the agent gets worse

A judge rewarded "accuracy". Within a week the agent learned to hedge, because hedged answers are never wrong. Accuracy went up and usefulness went down.

practitioner report

The average improves, a dangerous call appears

Agents made unsafe tool calls in 10.6% of cases, 21.5% in file and database work. A mean score can hide that.

RAIL Guard, arXiv 2607.16215

More iterations make it worse

In one study, held-out quality peaked at steps 4 to 7 and fell after. A loop with no stop rule keeps "improving" past the peak.

arXiv 2603.13791

Small sets backfire

With 30 training examples, GEPA's optimized prompt scored 34.0% against 62.4% for the prompt it started from.

arXiv 2602.22483

A crash costs the run twice

A rate limit or kill mid-run. In our IFBench run, GEPA restarted from zero and paid 600 calls again. Mutara repaid 11.

How it works

One loop: improve, accept, prove.

Each candidate passes three checks, and each check uses data the earlier step never saw. Every proposal, score and decision goes to a journal in SQLite.

01 · Improve

Rewrite from failures

Your reflection model sees the failed train cases, their traces and your scorer's feedback, then rewrites the prompt. It never sees validation or final cases. Prompt length is capped per component, so it can't grow into a lookup table.

02 · Accept

Win on validation, break no rule

A rewrite becomes the new champion only if it scores higher on validation cases and adds no hard-rule violations. Rounds and a cost budget are set before the run.

03 · Prove

Test on fresh cases

The champion faces your original prompt on cases used for nothing else. A paired, anytime-valid test stops as soon as the answer is clear: promote, reject, or inconclusive. Inconclusive is not a pass.

The champion is not deployed for you. You apply it through your own config, keep the previous version, and roll back from the journal if production disagrees.

Hard rules

A forbidden action can't be traded for a better average.

Your scorer returns two numbers per case: a score and a violation count. Scores are averaged. Violations are not: a candidate with more violations than its parent is rejected, at every step, however high its score.

// score one agent run: right tool, right args, no forbidden call
import { calledTool } from "./vercel-ai.mjs";

const score = (receipt, c) => {
  const calls = receipt.output.toolCalls;
  const graded = calledTool(calls, c.expected.tool, { args: c.expected.args });
  const cancelled = calls.some((t) => t.name === "cancel_order");
  return {
    ...graded,
    // hard rule: never cancel unless the user asked to
    violation: cancelled && !c.expected.cancel ? 1 : 0,
  };
};

What counts as a hard rule

Anything you would roll back for even if quality went up: an irreversible tool call without a request, a refund over a limit, broken JSON, a leaked field. Write it as code, not as a judge prompt, so the optimizer can't argue with it.

Mutara checks versions before they ship. It does not intercept tool calls at runtime. Keep your runtime guardrails; Mutara makes sure a new prompt doesn't lean on them more.

Wiring

Your generateText, your model, your tools.

Copy vercel-ai.mjs from the package into your project. Mutara has no dependency on ai; it calls the function you pass. The runner sees only case inputs, never the expected answers.

import { generateText } from "ai";
import { optimizeReflective, buildReflectionPrompt } from "teob-mutara/reflective";
import { toolCallsOf, usageCost } from "./vercel-ai.mjs";

const run = async (system, c) => {
  const r = await generateText({ model, system, prompt: c.input.text, tools });
  return { output: { text: r.text, toolCalls: toolCallsOf(r) }, cost: usageCost(r.usage) };
};

const result = await optimizeReflective({
  id: "support-agent-v1", storage: "./mutara.db",   // same id after a crash = resume
  implementation: { model: "gpt-4.1-mini", tools: Object.keys(tools), scorer: "tools-v1" },
  initialPrompt: SYSTEM_PROMPT,
  objective: "Resolve support requests with the right tool. Never cancel unless asked.",
  cases, finalCases,                                // finalCases: used only for the last test
  run, score,                                       // score from the Hard rules section
  reflect: async ({ objective, parentPrompt, failures, parentScores }) => {
    const r = await generateText({ model: strongModel,
      prompt: buildReflectionPrompt(objective, parentPrompt, failures, parentScores) });
    return { text: r.text, cost: usageCost(r.usage) };
  },
  rounds: 6, maxPromptChars: 4000, budget: { cost: 3_000_000 },
  finalTest: { scoreRange: 1 },
});

console.log(result.champion, result.finalAudit);

FAQ

Questions from agent builders.

Is the search better than GEPA?

No. The reflective search follows GEPA's idea: reflect on failures, keep a Pareto front, merge components. What differs is everything around it: held-out acceptance, hard rules, the final test, the journal and resume. If you prefer another search, plug it in through Adapter and keep the rest.

My agent takes several steps. How do I score it?

Your scorer gets the whole receipt: final text, every tool call and the trace. Helpers check which tools were called, with which arguments, and in which order. Anything else you can check in code, you can score or mark as a violation.

How many cases do I need?

A clear improvement often resolves within a few dozen fresh pairs, because the test stops early. Proving a cheaper setup is no worse costs more: about 120 pairs for a 0.05 margin on a 0–1 score, 200 for 0.03, 300 for 0.02. Production logs with known outcomes work well as cases.

What does a run cost?

The extraction benchmark took 86–121k tokens for the whole run. You set a cost budget and a per-call limit. After a crash, the same id resumes and finished calls are not paid again.

What if a call has side effects?

Use recovery: "manual". A call that was in flight at a crash blocks for you to reconcile instead of running twice.

Can feedback come later, or from a person?

Yes, through a custom Adapter: a grade can return later, and the experiment waits for it in the journal.
